このページでは、FishXCode の課金基準、トークングループ、プランのページの関係を説明します。プランの購入や Key の作成前のチェックリストとして活用してください。まず料金ページでモデルとプランを確認し、次にグループを見て Key で何を呼び出せるかを決め、最後に使用ログとグループ稼働状況で実際の消費を照合します。

</Callout>

## 1. まず 3 種類の課金方式を区別する

FishXCode の料金は単一のルールで決まるわけではありません。実際に利用する際は、まずどの方式を使っているかを確認してください：

| 方式 | 確認するポイント | 向いている場面 |
| - | - | - |
| 従量利用 | モデルの基本価格、入力／出力／キャッシュの倍率、トークングループ | 残高による API 呼び出し、一時的なテスト、複数モデルの併用 |
| サブスクリプションプラン | 有効期間、総利用枠、1 日の上限、1 か月の上限、対象グループ | チームの固定予算、Codex / Claude シリーズの長期利用 |
| トークングループ | その Key で呼び出せるモデル、利用するリソースプール、適用される課金倍率 | Key の作成、プロジェクトの分割、チームのコスト配分 |

プランのルールは [サブスクリプションプラン概要](/ja/subscription-plans) とあわせてご覧ください。このページでは「モデル・倍率・グループが課金にどう影響するか」を、プランのページでは「購入後の利用枠・有効期間・回数・上限がどのように適用されるか」を説明しています。

## 2. 料金ページ：まずプランカードを見る

料金ページのプランカードを見れば、そのプランで得られる利用枠や回数、有効期間、1 日に使える量、特別な換算ルールの有無をすばやく判断できます。

![サブスクリプションプラン一覧の例](/img/plans/subscription-plans.png)

プランカードでは、次の項目を重点的に確認してください：

| 項目 | 意味 | 判断のしかた |
| - | - | - |
| 現在の価格 | 今回の購入価格と有効期間 | 例：`¥320.00 / 1か月` は 1 か月分の価格を表します |
| 1 回あたりのコスト | プラン価格を総回数で割った参考コスト | 同種の回数制プランのコストパフォーマンスを比較するのに使います |
| プラン上限 | 現在のプランの総利用枠または総回数 | 例：`15000 回` は、このプランで基本リクエストを累計最大 15000 回まで利用できることを表します |
| 1 日の上限 | 1 日に利用できる利用枠または回数の上限 | 例：`500 回/日`。当日の上限に達すると、通常はリセットを待つ必要があります |
| リセット時刻 | 期間ごとの上限が回復する時刻 | 例：`毎日 08:00:00 にリセット` |
| 対象範囲 | プランに紐付くグループ、モデル、プロバイダー | 例：`sub_plan_claude_mini_plus · 9 モデル · 2 プロバイダー` |
| 回数制課金の説明 | 特定のモデルを倍率で回数換算するかどうか | 例：Claude Opus 4.8、GPT-5.5 は `2.5 * 1 回` として計算 |

<Callout type="idea" title="例：回数制プランの差し引き方">
  あるプランに `500回/日、月合計15000回` と書かれ、`Claude Opus 4.8、GPT-5.5 は 2.5 * 1 回として計算` と説明されているとします。

  通常のモデルでリクエストが 1 回成功すると、通常は 1 回として記録されます。Claude Opus 4.8 や GPT-5.5 でリクエストが 1 回成功すると、2.5 回分としてプランの利用量に計上されます。つまり、その日にこうした高倍率のモデルだけを使い続けると、約 200 回のリクエスト成功で `500回/日` の 1 日上限に達する可能性があります。
</Callout>

## 3. プランの特典：上限、リセット、対象モデルを確認する

プランの特典ページや詳細ページを開くと、より詳しい特典の項目を確認できます。このモジュールは「購入後に実際に何が使えるのか」を確かめるためのものです。

![回数制プランの特典の例](/img/plans/by-number-of-times.png)

この画像では、次の内容を確認できます：

- **1 日の上限**：1 日に利用できる最大回数。
- **プラン上限**：有効期間全体での総回数。
- **リセット時刻**：1 日の上限が回復する時刻。
- **購入受付期間**：一部のプランは、指定された期間のみ購入できます。
- **プロバイダー**：プランが対象とする上流プロバイダー。
- **利用可能なモデル**：購入後、このプランのグループで呼び出せるモデルの一覧。
- **アップグレードグループ**：購入後に自動で移行または紐付けされるグループ。例：`sub_plan_claude_mini_max`。

<Callout type="warn" title="プランのページとグループはあわせて確認する">
  プランのページは「利用枠と上限」を、グループは「モデルとチャネル」を示します。プランがあるアップグレードグループに対応していると表示されていても、実際の Key がそのプランやグループに紐付いていなければ、リクエストが残高から差し引かれたり、権限エラーになったりする可能性があります。
</Callout>

## 4. 購入：支払い前に有効期間と開通方法を確認する

購入をクリックすると、購入ダイアログが開きます。ここでは、どのプランを買うのか、金額、有効期間の長さ、自動で開通するかどうかを最終確認します。

![サブスクリプションプラン購入の例](/img/plans/buyplan.png)

購入前に重点的に確認する項目：

| 項目 | 重要な理由 |
| - | - |
| 現在の価格 | 今回の支払金額を確認し、プランの選び間違いを防ぐため |
| 有効期間 | 期限が過ぎるとプランの特典が失効するため |
| トークン利用枠 / 回数 | このプランで消費できる総量が決まるため |
| プランの種類 | 自動開通、手動での付与、その他の納品方法によって適用開始時期が変わるため |
| 支払い方法 | Alipay、WeChat Pay、その他の支払い窓口を確認するため |
| 購入時の注意事項 | 返金、開通、購入制限、アフターサポートのルールはページの表示が優先されるため |

モデルを一時的に試したいだけなら、先にプランを買う必要はありません。まず残高で従量課金として呼び出すこともできます。

## 5. 従量利用：残高で直接モデルを呼び出す

従量利用とは、固定のプランを購入せずに、アカウント残高で直接モデルを呼び出す方法です。まずツールの動作を確認したいとき、呼び出しの頻度が低いとき、複数のモデルを併用するとき、どのプランを買うかまだ決めていないときに向いています。

従量利用の基本的な流れ：

1. [料金ページ](https://fishxcode.com/pricing?currency=CNY) で、目的のモデルがどのグループに対応しているかを確認します。
2. **コンソール → トークン管理** で通常トークンを作成し、適切なトークングループを選択します。
3. Key を Claude Code、Codex、Cursor、RooCode、または自社のプログラムに設定します。
4. リクエストが成功するたびに、モデル価格、入力／出力トークン、キャッシュヒット、グループ倍率に基づいて残高から差し引かれます。
5. **コンソール → 使用ログ** で実際の消費を照合します。

従量課金の差し引き額は、次のように考えることができます：

```text
実際の消費 ≈ モデルの基本消費 × グループ倍率 + 出力/キャッシュなどの差分
```

ここでいう「モデルの基本消費」は固定値ではなく、入力の長さ、出力の長さ、キャッシュヒット、モデル自体の価格によって変わります。画像や動画などの固定価格のモデルは、通常のテキストのトークン方式で見積もるのには向きません。

残高による従量課金とプランの違い：

| 種類 | 特徴 | 向いている場面 |
| - | - | - |
| 残高による従量課金 | 使った分だけ差し引かれ、残高が不足すると呼び出しが止まる | 一時的なテスト、複数モデルの併用、低頻度の利用 |
| Codex プラン | 通常は有効期間と利用枠で管理される | Codex / GPT のプログラミングタスク、チームの固定予算 |
| 回数制プラン | 成功したリクエストの回数で累計され、1 日の上限が設定されている場合がある | リクエスト回数で予算を管理したい場合 |
| ClaudeMax プラン | アカウントの特典と Claude Code での利用が中心 | Claude Code 公式アカウントのサブスクリプション利用 |

<Callout type="idea" title="例：従量利用が向いているケース">
  あるツールが FishXCode に接続できるかを試したいだけなら、まず `default` または目的のモデルの推奨グループで通常トークンを作成し、少量のリクエストを送れば十分です。モデル、グループ、クライアント設定がすべて正しいことを確認してから、利用量に応じて Codex プラン、回数制プラン、ClaudeMax プランを購入するかどうかを決めましょう。
</Callout>

<Callout type="warn" title="従量利用もグループの制限を受ける">
  アカウントに残高があっても、どの Key でもすべてのモデルを呼び出せるわけではありません。モデルを利用できるかどうかは、引き続きトークングループで決まります。`model not found`、`model not available`、または権限エラーが出た場合は、まず Key のグループに目的のモデルが含まれているかを確認してください。
</Callout>

## 6. トークン：グループが Key のモデル範囲を決める

トークングループは、**その API Key で利用できるモデルの範囲 + 課金倍率のルール + 上流リソースプール** と考えることができます。Key を作成するときは、必ず正しいグループを選んでください。

![トークン作成時のグループ選択](/img/start/api-06-token-create.png)

通常トークンを作成するときに重点的に確認する項目：

- **トークングループ**：この Key で呼び出せるモデルを決めます。
- **利用枠の設定**：この Key で消費できる利用枠の上限を設定します。利用枠を無制限にしても課金されないわけではなく、アカウント残高やプランの制限は引き続き適用されます。
- **モデル制限リスト**：特定のモデルだけを許可したい場合を除き、制限はおすすめしません。
- **IP ホワイトリスト**：送信元 IP が固定されたサーバー向けです。個人のローカル開発では、IP が変わって呼び出せなくなるおそれがあるため、慎重に使ってください。

グループを間違えた場合によくある症状：

- モデル一覧にはモデルが表示されるのに、現在の Key で呼び出すと `model not found`、`model not available`、または権限エラーが出る。
- モデルは呼び出せるが、課金倍率、キャッシュの効き方、安定性が想定していたランクと異なる。
- プラン用の Key と通常の残高用の Key を混用し、利用枠が想定外のアカウントから差し引かれたり、集計基準が不明確になったりする。

## 7. プラントークン：プランに基づいてチームの Key を作成する

プランを購入すると、システムがプラン用のアクセストークンを自動生成する場合があります。また、プランに基づいて新しいチーム用トークンを作成することもできます。複数人でプランの利用枠を共有しつつ、メンバーやプロジェクトごとの消費を区別したい場合に適しています。

![プランに基づくトークン作成の例](/img/plans/create.png)

プランに基づいてトークンを作成するときは、次の項目を重点的に確認してください：

| 項目 | 説明 |
| - | - |
| プランに基づいて作成 | 紐付けるプランを選択します。紐付け後は、有効期限、グループ、モデル制限がプランに従います |
| 名前 | ログで絞り込みやすいよう、メンバー、プロジェクト、サービスごとに命名することをおすすめします |
| トークングループ | デフォルトではプランまたはユーザーのグループに従います。合わないグループに安易に切り替えないでください |
| 有効期限 | 通常はプランの有効期間を超えないようにします |
| プラントークンの利用枠 | このサブ Key が消費できるプラン利用枠の上限を設定します |

<Callout type="idea" title="例：チームでの Key の分け方">
  1 つの Codex プランを 5 人のメンバーで共有する場合、全員で同じ Key を使うのはおすすめしません。メンバーごとに個別のトークンを作成しましょう。例：`codex-zhangsan`、`codex-lisi`。そうすれば、使用ログやグループ稼働状況で、誰の消費が多いか、誰のエラーが多いか、どのプロジェクトに上限が必要かをすぐに把握できます。
</Callout>

トークン一覧には、グループ、倍率、利用可能なモデル、有効期限が表示されます：

## 9. 倍率と課金の例

倍率は、モデルの基本価格にさらに掛ける係数にすぎません。倍率が低いほど、同じモデル・同じリクエストでの差し引き額は通常少なくなります。

| モデルの基本消費 | グループまたはモデルの倍率 | 差し引き額の目安 |
| - | - | - |
| 10 クレジット | `1x` | 10 クレジット |
| 10 クレジット | `0.5x` | 5 クレジット |
| 10 クレジット | `0.1x` | 1 クレジット |
| 10 クレジット | `2.5x` | 25 クレジット |

実際の呼び出しに近い例：

| 場面 | 見積もり方 |
| - | - |
| あるモデルの基本消費が 8 クレジットで、`1x` の基準で計算される場合 | 約 8 クレジットが差し引かれます |
| 同じリクエストが `0.5x` の基準で計算される場合 | 約 4 クレジットが差し引かれます |
| 同じリクエストに `2.5x` のモデル倍率が適用される場合 | 約 20 クレジットが差し引かれます |
| キャッシュにヒットした長いコンテキストのリクエスト | キャッシュ部分は通常割安になります。最終的にはログの記録が優先されます |

<Callout type="warn" title="倍率だけで判断しない">
  倍率は価格を決める唯一の要素ではありません。モデルごとに基本価格、出力倍率、キャッシュ倍率は大きく異なり、画像や動画のモデルは固定価格の場合もあります。コストを見積もる際は、料金ページまたはコンソールのモデル一覧に表示されている現在の価格を基準にしてください。
</Callout>

## 10. 利用後に実際の消費を照合する方法

呼び出した後は、見積もりだけで費用を判断せず、**コンソール → 使用ログ** で実際の消費を確認してください。チームやプランで利用している場合は、さらに **グループ稼働状況** とあわせて、単一の Key、単一のユーザー、グループ全体のどこに問題があるかを判断します。

![グループ稼働状況の例](/img/plans/statistics.png)

グループ稼働状況は、次のような疑問に答えるのに適しています：

| 疑問 | 確認する項目 |
| - | - |
| どのグループの消費が最も多いか | グループ、消費、リクエスト数 |
| 特定のメンバーだけが異常なのか | ユーザー / トークンの明細行 |
| キャッシュが効いているか | キャッシュヒット率、キャッシュトークン数、キャッシュリクエスト率 |
| リソースプールの問題か | グループの成功率、エラー数、失敗原因 |
| 長いコンテキストや大量の出力で費用が高くなっていないか | 1 回の成功あたりの消費、平均所要時間、キャッシュトークン数 |

<Callout type="idea" title="例：チームでの振り返り">
  `codex_sub` グループ全体の成功率は正常なのに、あるメンバーのトークンの 1 回の成功あたりの消費が他のメンバーより明らかに高い場合は、まずそのメンバーが長いコンテキスト、大量の出力、重複したタスクを実行していないかを確認します。グループ全体の成功率が下がっている場合は、グループのリソースプール、上流の状態、プランの権限の問題を検討します。
</Callout>

## 11. クイック選択ガイド

| 利用シーン | まず確認するもの | 理由 |
| - | - | - |
| 何を使えばよいかわからない | `default` またはコンソールの推奨グループ | まずツールの設定が正しいかを検証するため |
| Claude Code を安定して使いたい | `cc-max`、`cc_max`、ClaudeMax シリーズ | Claude Code の利用経路により適しているため |
| 自社クライアントで Claude に接続したい | `cc_export` | クライアントを制限せず、サードパーティツールに適しているため |
| Codex / GPT でのプログラミング | `codex_plus`、`codex_pro`、`codex_sub_june` | コーディングやツール呼び出しのタスク向けのため |
| 複数シリーズを統一入口で使いたい | `OpenRouter` | Claude、Codex など複数シリーズのモデルを統一入口から呼び出すのに適しているため |
| Gemini CLI やマルチモーダル | `gemini` | Gemini シリーズのモデルをカバーしているため |
| Grok モデル | `grok` | Grok の対話、推論、ビジョンのタスクをカバーしているため |
| DeepSeek モデル | `deepseek` | DeepSeek の公式チャネルをカバーしているため |
| チームやプロジェクトで分けたい | メンバーやプロジェクトごとに個別のトークンを作成 | 利用枠の管理、コストの按分、ログでの調査がしやすいため |

## 12. 消費や権限の異常を調査する

消費の異常やモデルが使えない問題が起きたときは、次の順序で調査することをおすすめします：

1. 現在の Key に紐付いたトークングループに、目的のモデルが含まれているかを確認します。
2. 残高、プランの有効期間、1 日の上限、1 か月の上限、総利用枠が十分かを確認します。
3. **コンソール → 使用ログ** を開き、時刻、モデル、トークン、グループ、リクエスト ID で絞り込みます。
4. [グループ稼働状況](/ja/group-health) と比較し、単一のトークンの問題か、グループのリソースプールの問題かを判断します。
5. それでも判断できない場合は、サポートへの問い合わせ時に注文番号、トークン名、グループ、モデル名、リクエスト時刻、リクエスト ID を伝えてください。
