グループ稼働状況は、呼び出しの異常が単一リクエストの問題なのか、特定のプラン、モデル、上流グループ、チームメンバーに集中した問題なのかを判断するためのものです。企業やチームの管理者は、これを使って次の 3 つの疑問にすばやく答えられます：

- 指定した期間内に、どのグループの成功率が下がっているか
- 主なリクエスト量、消費、エラーを生んでいるのはどのユーザーまたはトークンか
- エラーが単一のトークンに集中しているのか、すでにグループ全体に影響しているのか

API の異常を調査するときは、まずグループ稼働状況を確認し、次に個々の使用ログで具体的な `request_id` を特定します。

<Callout type="info" title="データの集計範囲">
  このページに埋め込まれている公開 `status` ページは、選択した期間内に FishXCode プラットフォームの全ユーザーが利用しているグループの稼働状況を集計しており、プラットフォーム全体のグループの可用性を反映しています。リアルタイム性、公正性、安定性を備えています。

  コンソール内の **使用ログ → グループ稼働状況** は、現在のアカウントの権限で閲覧できるデータを集計します。個人ユーザーは通常、自分のトークンのみを確認できます。企業やチームの管理者は、ユーザー、ユーザー名、トークン、グループの各軸でチームの利用状況を確認できます。
</Callout>

上のステータスページが正しく読み込まれない場合は、[FishXCode グループ稼働状況](https://status.fishxcode.com/group/global?view=list&sort=group&window=24h) を直接開いてください。

コンソールの入口：[コンソール → 使用ログ](https://fishxcode.com/console/log)。エラーログまたは統計ビューで、期間、モデル、トークン、グループ、エラーメッセージ、ステータスコードで絞り込めます。

![コンソールのグループ稼働状況の例](/img/group-health.png)

<Callout type="idea" title="使い方の原則">
  まず影響範囲を判断し、それから個々のエラーに対処します。単一のログは具体的なリクエストの特定に、グループ稼働状況は問題が集中して発生しているかどうかの判断に適しています。

個々のエラーメッセージの意味を知りたい場合は、[エラーログ解説](/ja/error-logs) をご覧ください。

## 一覧の表示項目

コンソールの一覧と CSV エクスポートの表示列は同じです。一覧には 2 種類の行が表示されます：

- **グループ行**：1 つのグループについて、現在の期間内の全体的な稼働状況を集計します。
- **トークン行**：あるグループ配下のユーザーとトークンの明細を表示し、企業やチームの管理者がメンバー、プロジェクト、サービスを特定しやすくします。

| 表示項目 | 対象の行 | 項目の説明 | 活用のポイント |
| - | - | - | - |
| 種別 | グループ行、トークン行 | その行が `グループ` の集計か `トークン` の明細かを示します | まずグループ行で全体の状態を判断し、次にトークン行で具体的なメンバーやトークンを特定します |
| グループ | グループ行、トークン行 | 現在の期間内に出現したグループ。従量課金グループ、プラングループ、デフォルトグループ、特定モデルのグループを含みます | 問題が特定のプラン、モデル、上流リソースプールに集中しているかを判断します |
| ユーザー ID | トークン行 | そのトークンを使用したユーザーの ID | 企業での調査時に、メンバーのアカウントを特定するのに使います |
| ユーザー名 | トークン行 | そのトークンを使用したユーザーの名前 | チームのレポート、メンバーとのやり取り、権限の確認に使います |
| トークン | トークン行 | コンソールで設定したトークン名 | 異常が特定のトークンだけに集中しているかを判断します |
| 成功率 | グループ行、トークン行 | 成功率 = 成功回数 / 総リクエスト数 | 80% を下回ったら注意が必要です。同じグループの他の行より明らかに低い場合は、そのグループまたはトークンを優先して調査します |
| リクエスト数 | グループ行、トークン行 | 現在の期間内の総リクエスト数 | サンプル数が少ないときは、成功率を過度に解釈しないでください |
| 成功 | グループ行、トークン行 | 2xx を返した成功リクエストの回数 | 「リクエスト数」「エラー」とあわせて全体の可用性を判断します |
| エラー | グループ行、トークン行 | エラー（4xx/5xx）を返したリクエストの回数 | エラー数が増えたときは、まず「失敗原因」とエラーログを確認します |
| 消費 | グループ行、トークン行 | 現在の期間内に累計した利用枠の消費。エクスポート時は金額で表示されます | チームのコスト計算、プロジェクトごとの按分、異常な消費の発見に使います |
| キャッシュヒット率 | グループ行、トークン行 | キャッシュヒット率 = キャッシュにヒットしたトークン / 総トークン | 高いほど費用を抑えられます。ヒットした部分は通常、低価格または無料で計算されます |
| キャッシュトークン数 | グループ行、トークン行 | 現在の期間内にキャッシュにヒットしたトークン数 | この部分は通常、大幅に割り引かれた価格で計算されるため、多いほど節約になります |
| キャッシュリクエスト数 | グループ行、トークン行 | 少なくとも 1 回キャッシュにヒットしたリクエストの回数 | 実際にキャッシュを活用したリクエストがどれだけあるかを測ります |
| キャッシュリクエスト率 | グループ行、トークン行 | キャッシュリクエスト率 = キャッシュにヒットしたリクエスト / 総リクエスト | 高いほど、多くの呼び出しがキャッシュ割引の恩恵を受けています |
| 平均キャッシュトークン数 | グループ行、トークン行 | キャッシュヒット 1 回あたりの平均トークン数 | メンバー、サービス、グループ間でキャッシュの利用効率を比較するのに使います |
| 平均所要時間 | グループ行、トークン行 | 1 リクエストあたりの平均所要時間（単位：秒） | 短いほど上流の応答が速いことを示します。所要時間が増えた場合は、長いコンテキスト、長い出力、ツールの呼び出し経路を調べます |
| 開始時刻 | グループ行、トークン行 | 現在の期間内に、そのグループまたはトークンが最初に出現した時刻 | 問題や呼び出しが始まった時刻を特定します |
| 最終リクエスト | グループ行、トークン行 | 現在の期間内に、そのグループまたはトークンが最後に出現した時刻 | 問題や呼び出しがまだ続いているかを判断します |
| 失敗原因 | グループ行 | 出現頻度の高い失敗原因の上位数件（ステータスコードと回数を含む）。エラーがない場合は空欄または `-` | 回数の多いエラーから優先して対処し、最後のログだけで判断しないでください |

<Callout type="info" title="項目の出典">
  表示項目は、バックエンドの統計データを集計して生成されています。日常の利用ではコンソールの一覧と CSV エクスポートの列を基準にしてください。API と連携する場合や技術的な調査を行う場合にのみ、基盤となるフィールド名と照らし合わせる必要があります。
</Callout>

<Callout type="idea" title="チームでの特定方法">
  まずグループ行でリソースプールの問題かどうかを判断し、次にトークン行で特定のユーザーやトークンが原因かどうかを判断します。グループの成功率は正常なのに単一のトークンのエラー率が高い場合は、通常、そのメンバーのトークン、モデル名、クライアント設定、リクエストボディを優先して調査します。
</Callout>

## CSV エクスポートについて

CSV エクスポートは、現在の一覧を同じ列のまま書き出す機能です。企業やチームの週次レポート、コストの按分、異常の振り返り、メンバーの利用量の照合に適しています。

エクスポート後は、[オンライン CSV ビューアー](https://tools.beer/zh/csv/viewer/) で開いてプレビューできます。このツールは CSV ファイルのドラッグ＆ドロップや選択に対応しており、CSV テキストを貼り付けることもできるため、列の内容や失敗原因をすばやく確認するのに便利です。

| エクスポートの表示 | 説明 |
| - | - |
| グループ行 | `種別` が `グループ` で、ユーザー ID、ユーザー名、トークンは通常空欄です。そのグループ全体の集計を表します |
| トークン行 | `種別` が `トークン` で、ユーザー ID、ユーザー名、トークン名が表示されます。そのグループ配下のメンバーまたはトークンの明細を表します |
| 金額の形式 | `消費` はコンソールの金額形式で表示されます。例：`¥905.48` |
| パーセントの形式 | 成功率、キャッシュヒット率、キャッシュリクエスト率はパーセントでエクスポートされます |
| 数値の形式 | 大きな数値には 3 桁区切りのカンマが付く場合があり、そのまま読んだり表計算ツールに取り込んだりできます |
| 時刻の形式 | 開始時刻と最終リクエストはローカル時刻でエクスポートされるため、問題の発生時刻と照らし合わせやすくなっています |
| 失敗原因 | 頻度の高い複数のエラーがまとめて表示され、末尾に出現回数が付きます。エラーがない場合は空欄または `-` です |

## 調査の流れ

### 1. 影響範囲を判断する

まず `種別=グループ` の集計行を確認します。「成功率」が通常の水準に近く、「エラー」も少なければ、多くの場合は偶発的なエラーです。個々のリクエストの `request_id` をコピーして調査を続けてください。

あるグループの「成功率」が他のグループより明らかに低い場合や、「エラー」が集中して増えている場合は、グループ単位でモデル、トークン、上流アカウント、プランの権限、プラットフォームのリソース状態を優先して調査します。

企業やチームで利用している場合は、さらにそのグループ配下の `種別=トークン` の明細行を確認します。特定のユーザーやトークンだけが異常な場合は、そのメンバーのクライアント設定、トークン、モデル名、リクエストボディ、同時実行の方針を優先して調査します。

### 2. 上位のエラー原因を確認する

「失敗原因」は通常、出現回数の順に表示されます。調査では、まず最も頻度の高いエラーに対処し、その後で頻度の低いエラーを確認します。頻度の高いエラーは、現在の期間内の主な障害の種類を反映しています。

| エラーの種類 | よく見られるログのキーワード | 一次判定 | 優先して確認すること |
| - | - | - | - |
| レート制限 | `Account RPM limit exceeded`、`Max 10/min`、`Max 5/min` | 利用上の問題または上流の制限 | 同時実行数や 1 分あたりのリクエスト数が多すぎる |
| 1 日の利用上限 | `Account daily limit exceeded` | 上流の制限 | 上流アカウントの本日の利用枠を使い切った |
| 認証情報のクールダウン | `All credentials ... are cooling down` | 上流の制限 | 現在のモデルの上流認証情報がすべてクールダウン中 |
| リクエストボディが大きすぎる | `status_code=413`、`openai_error` | 利用上の問題 | コンテキスト、ファイル、画像、ツールの結果が大きすぎる |
| 権限または認証 | `401`、`403`、`Invalid API key`、`pending admin approval` | 利用上の問題またはアカウントの状態 | トークン、プラン、グループ、モデルの権限に異常がある |
| 利用可能なリソースがない | `No available accounts`、`No available channel`、`auth_unavailable` | プラットフォームの問題または設定の問題 | 現在のグループに利用可能なアカウント、チャネル、認証リソースがない |
| 上流の異常 | `502`、`all upstreams failed`、`Upstream request failed` | 上流の問題 | 上流サービスまたは途中のネットワークの異常 |
| ゲートウェイのタイムアウト | `504`、`521`、`522`、`524` | 上流の問題または経路の問題 | 上流への接続、読み取り、応答のタイムアウト |
| プラットフォームのリソース保護 | `system disk overloaded`、`Service Unavailable` | プラットフォームの問題 | プラットフォームのノードまたは上流リソースが一時的に利用できない |
| 画像 API の形式 | `gpt-image-2`、`prompt is required`、`multipart form` | 利用上の問題 | 画像 API のパス、プロンプト、アップロード形式の誤り |
| ツール呼び出しの形式 | `tool_use`、`tool_result`、`Invalid schema` | 利用上の問題 | クライアントのツールメッセージまたは JSON Schema が要件を満たしていない |

### 3. 影響範囲に応じて対処する

| 現象 | 考えられる原因 | 推奨される対処 |
| - | - | - |
| 単一のトークンだけでエラーが出る | トークンの設定、権限、ローカルのリクエスト形式の問題 | トークンをコピーし直し、クライアント設定とリクエストボディを確認する |
| 単一のモデルだけでエラーが出る | モデルの権限、モデルのチャネル、上流のモデルリソースの問題 | 同種のモデルに切り替え、現在のプランがそのモデルに対応しているかを確認する |
| 単一のグループだけ成功率が低い | グループのリソースプール、プランの権限、上流アカウントの問題 | グループ／モデルを切り替える。サポートに問い合わせる際はグループ名と期間を伝える |
| 複数のグループで同時に `502`、`504`、`521`、`522`、`524` が出る | 上流またはネットワーク経路の異常 | しばらくしてから再試行し、長時間のタスクを減らす。続く場合はサポートに連絡する |
| 複数のリクエストで `413` が出る | リクエストボディが大きすぎる | コンテキストを短くし、ファイルを分割し、画像を圧縮するか、ツールの結果を減らす |
| 複数のリクエストで `429` が出る | リクエスト頻度が高すぎる、1 日の利用枠を使い切った、または認証情報のクールダウン | 同時実行数を下げる。ログで RPM、daily limit、cooling down を見分ける |

### 4. 消費とキャッシュをあわせて確認する

| 現象 | 考えられる原因 | 推奨される対処 |
| - | - | - |
| 「消費」が同じグループの他のトークンより明らかに多い | 大きなコンテキスト、長い出力、高頻度の呼び出し、重複したタスク | リクエスト数、平均所要時間、エラーログをあわせて確認し、具体的なサービスやメンバーを特定する |
| 「キャッシュヒット率」は高いが「キャッシュリクエスト率」が低い | 少数の大きなリクエストがキャッシュにヒットしている | 特定のタスクだけがコンテキストを再利用していないかを確認する |
| 「キャッシュリクエスト率」は高いが「平均キャッシュトークン数」が低い | 多くのリクエストがキャッシュにヒットしているが、1 回あたりの効果が小さい | コンテキストが短すぎないか、キャッシュの内容が安定しているかを確認する |
| 単一のトークンの「平均所要時間」が明らかに長い | クライアントのタスクが重い、コンテキストや出力が長い、または上流が遅い | そのトークンのリクエスト数、キャッシュ、失敗原因、個々のログを比較する |

## サポートでの調査に必要な情報

簡単な問題であれば、まず [エラーログ解説](/ja/error-logs) と [グループ稼働状況の説明](/ja/group-health) を見て自分で確認することをおすすめします。それでも解決しない場合は、`console/log` のエラーログ詳細でコピーアイコンをクリックすると、調査用の内容をワンクリックでコピーできます。サポートに連絡する際は、やり取りの回数を減らせるよう、次の情報をまとめて技術担当者に伝えてください：

- ユーザー ID
- 期間：問題が始まった時刻と最後に発生した時刻
- グループ名：`group`
- モデル名：リクエストで使用したモデル
- ステータスコード：`429`、`413`、`502`、`503` など
- エラー内容：`error_reasons.content`
- リクエスト ID：個々のログまたは API レスポンスに含まれる `request_id`
- 影響範囲：単一のトークン、単一のモデル、単一のグループか、複数のグループで同時に異常が起きているか

<Callout type="idea" title="早見まとめ">
  `401` / `403` は主に権限、`413` は主にリクエストボディ、`429` は主に頻度と利用枠、`502` / `504` / `524` は主に上流と長時間のタスク、`503` は主にリソースが一時的に利用できないかどうかを確認します。
</Callout>
