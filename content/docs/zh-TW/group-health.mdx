分組健康狀態用於判斷呼叫異常是單個請求問題，還是某個套餐、模型、上游分組或團隊成員的集中問題。企業和團隊管理員可以用它快速回答三個問題：

- 哪個分組在指定時間範圍內成功率下降
- 哪個使用者或令牌貢獻了主要請求量、消耗或錯誤
- 錯誤是集中在單個 Token，還是已經影響整個分組

排查介面異常時，先看分組健康狀態，再進入單條使用日誌定位具體 `request_id`。

<Callout type="info" title="資料口徑">
  本頁嵌入的公開 `status` 頁面查詢的是所選時間段內 FishXCode 整個平臺所有使用者正在使用的分組健康狀態，反映全平臺分組可用性，具備即時性、公正性和穩定性。

  控制台內的 **使用日誌 → 分組健康狀態** 按當前帳號許可權統計可見資料。個人使用者通常只看到自己的 Token；企業和團隊管理員可結合使用者、使用者名稱、令牌和分組維度檢視團隊使用情況。
</Callout>

如果上方狀態頁未正常載入，可直接開啟 [FishXCode 分組健康狀態](https://status.fishxcode.com/group/global?view=list&sort=group&window=24h)。

控制台入口：[控制台 → 使用日誌](https://fishxcode.com/console/log)。在錯誤日誌或統計檢視中，按時間範圍、模型、Token、分組、錯誤訊息和狀態碼篩選。

## 列表展示欄位

控制台列表和 CSV 匯出的展示列保持一致。列表同時展示兩類行：

- **分組行**：彙總一個分組在當前時間範圍內的整體健康狀態。
- **令牌行**：展示某個分組下的使用者和令牌明細，便於企業、團隊管理員定位成員、專案或服務。

| 展示欄位 | 適用行 | 欄位說明 | 使用建議 |
| - | - | - | - |
| 型別 | 分組行、令牌行 | 標識當前行是 `分組` 彙總，還是 `令牌` 明細 | 先看分組行判斷整體狀態，再看令牌行定位具體成員或 Token |
| 分組 | 分組行、令牌行 | 當前時間段內出現過的分組，包含按量分組、套餐分組、預設分組或特定模型分組 | 判斷問題是否集中在某個套餐、模型或上游資源池 |
| 使用者ID | 令牌行 | 使用該令牌的使用者 ID | 企業排查時用於定位成員帳號 |
| 使用者名稱 | 令牌行 | 使用該令牌的使用者名稱 | 用於團隊報表、成員溝通和許可權核對 |
| 令牌 | 令牌行 | 控制台中配置的 Token 名稱 | 判斷異常是否只集中在某個 Token |
| 成功率 | 分組行、令牌行 | 成功率 = 成功次數 / 總請求數 | 低於 80% 建議關注；明顯低於同組其他行時，優先排查該分組或令牌 |
| 請求數 | 分組行、令牌行 | 當前時間範圍內的總請求數 | 樣本量太小時不要過度解讀成功率 |
| 成功 | 分組行、令牌行 | 返回 2xx 的成功請求次數 | 與“請求數”“錯誤”一起判斷整體可用性 |
| 錯誤 | 分組行、令牌行 | 返回錯誤（4xx/5xx）的請求次數 | 錯誤數升高時，優先檢視“失敗原因”和錯誤日誌 |
| 消耗 | 分組行、令牌行 | 當前時間段累計的額度消耗，匯出時按金額展示 | 用於團隊成本核算、專案分攤和異常消耗識別 |
| 快取命中率 | 分組行、令牌行 | 快取命中率 = 命中快取的 Token / 總 Token | 越高越省錢；命中部分通常按低價或免費計算 |
| 快取Tokens | 分組行、令牌行 | 當前時間段命中快取的 Token 數 | 這部分通常按低折扣計價，越多越省 |
| 快取請求數 | 分組行、令牌行 | 至少命中一次快取的請求次數 | 衡量有多少請求實際用到了快取 |
| 快取請求佔比 | 分組行、令牌行 | 快取請求佔比 = 命中快取的請求 / 總請求 | 越高代表越多呼叫享受到了快取優惠 |
| 平均快取Tokens | 分組行、令牌行 | 平均每次命中快取的 Token 數 | 用於比較不同成員、服務或分組的快取利用效率 |
| 平均耗時 | 分組行、令牌行 | 平均每次請求耗時，單位為秒 | 越低代表上游響應越快；耗時升高時排查長上下文、長輸出和工具鏈路 |
| 開始時間 | 分組行、令牌行 | 當前時段內該分組或令牌首次出現的時間 | 定位問題或呼叫開始時間 |
| 最後請求 | 分組行、令牌行 | 當前時段內該分組或令牌最近一次出現的時間 | 判斷問題或呼叫是否仍在持續 |
| 失敗原因 | 分組行 | 出現頻率最高的幾條失敗原因，包含狀態碼和次數；無錯誤時為空或 `-` | 優先處理次數最多的錯誤，不要只看最後一條日誌 |

<Callout type="info" title="欄位來源">
  展示欄位由後臺統計資料聚合生成。日常使用以控制台列表和 CSV 匯出列為準；只有對接介面或技術排查時，才需要再對照底層欄位名。
</Callout>

<Callout type="idea" title="團隊定位">
  先看分組行判斷是否是資源池問題，再看令牌行判斷是否由某個使用者或令牌造成。如果分組成功率正常但單個令牌錯誤率高，通常優先排查該成員的 Token、模型名、客戶端配置或請求體。
</Callout>

## CSV 匯出說明

CSV 匯出就是把當前列表按相同列匯出，適合企業和團隊做週報、成本分攤、異常復盤和成員用量對賬。

匯出後可使用 [線上 CSV 檢視器](https://tools.beer/zh/csv/viewer/) 開啟預覽。該工具支援拖拽或選擇 CSV 檔案，也可以貼上 CSV 文本，適合快速檢查列內容和失敗原因。

| 匯出表現 | 說明 |
| - | - |
| 分組行 | `型別` 為 `分組`，使用者 ID、使用者名稱、令牌通常為空，表示該分組的整體彙總 |
| 令牌行 | `型別` 為 `令牌`，會展示使用者 ID、使用者名稱和令牌名稱，表示該分組下的成員或 Token 明細 |
| 金額格式 | `消耗` 以控制台金額格式展示，例如 `¥905.48` |
| 百分比格式 | 成功率、快取命中率、快取請求佔比會匯出為百分比 |
| 數字格式 | 大數字可能帶千分位分隔符，適合直接閱讀或匯入表格工具 |
| 時間格式 | 開始時間、最後請求會匯出為本地時間，便於和問題發生時間對齊 |
| 失敗原因 | 多個高頻錯誤會合並展示，並在末尾標出出現次數；無錯誤時為空或 `-` |

## 排查流程

### 一、判斷影響範圍

先看 `型別=分組` 的彙總行。如果“成功率”接近正常水平，且“錯誤”很低，通常是偶發錯誤，可複製單條請求的 `request_id` 繼續排查。

如果某個分組的“成功率”明顯低於其他分組，或“錯誤”集中升高，優先按分組排查模型、Token、上游帳號、套餐許可權和平臺資源狀態。

企業或團隊場景下，再看該分組下的 `型別=令牌` 明細行。如果只有某個使用者或令牌異常，優先排查該成員的客戶端配置、Token、模型名、請求體和併發策略。

### 二、再看 Top 錯誤原因

“失敗原因”通常按出現次數展示。排查時先處理最高頻錯誤，再看低頻錯誤。高頻錯誤能反映當前時間範圍內的主要故障型別。

| 錯誤型別 | 常見日誌關鍵詞 | 初步歸因 | 優先判斷 |
| - | - | - | - |
| 頻率限制 | `Account RPM limit exceeded`、`Max 10/min`、`Max 5/min` | 使用問題或上游限制 | 併發或每分鐘請求數過高 |
| 日額度限制 | `Account daily limit exceeded` | 上游限制 | 上游帳號今日額度已用盡 |
| 憑證冷卻 | `All credentials ... are cooling down` | 上游限制 | 當前模型上游憑證均處於冷卻期 |
| 請求體過大 | `status_code=413`、`openai_error` | 使用問題 | 上下文、檔案、圖片或工具結果過大 |
| 許可權或認證 | `401`、`403`、`Invalid API key`、`pending admin approval` | 使用問題或帳號狀態 | Token、套餐、分組或模型許可權異常 |
| 無可用資源 | `No available accounts`、`No available channel`、`auth_unavailable` | 平臺問題或配置問題 | 當前分組沒有可用帳號、通道或認證資源 |
| 上游異常 | `502`、`all upstreams failed`、`Upstream request failed` | 上游問題 | 上游服務或中間網路異常 |
| 閘道器超時 | `504`、`521`、`522`、`524` | 上游問題或鏈路問題 | 上游連線、讀取或響應超時 |
| 平臺資源保護 | `system disk overloaded`、`Service Unavailable` | 平臺問題 | 平臺節點或上游資源暫不可用 |
| 影像介面格式 | `gpt-image-2`、`prompt is required`、`multipart form` | 使用問題 | 影像介面路徑、提示詞或上傳格式錯誤 |
| 工具呼叫格式 | `tool_use`、`tool_result`、`Invalid schema` | 使用問題 | 客戶端工具訊息或 JSON Schema 不符合要求 |

### 三、按影響範圍處理

| 現象 | 更可能的原因 | 建議處理 |
| - | - | - |
| 只有單個 Token 報錯 | Token 配置、許可權或本地請求格式問題 | 重新複製 Token，檢查客戶端配置和請求體 |
| 只有單個模型報錯 | 模型許可權、模型通道或上游模型資源問題 | 切換同類模型，確認當前套餐是否支援該模型 |
| 只有單個分組成功率低 | 分組資源池、套餐許可權或上游帳號問題 | 切換分組/模型，聯絡支援時提供分組名和時間範圍 |
| 多個分組同時出現 `502`、`504`、`521`、`522`、`524` | 上游或網路鏈路異常 | 稍後重試，減少長任務；持續出現時聯絡支援 |
| 多個請求都出現 `413` | 請求體過大 | 縮短上下文，拆分檔案，壓縮圖片或減少工具結果 |
| 多個請求都出現 `429` | 請求頻率過高、日額度用盡或憑證冷卻 | 降低併發；根據日誌區分 RPM、daily limit 和 cooling down |

### 四、結合消耗和快取

| 現象 | 更可能的原因 | 建議處理 |
| - | - | - |
| “消耗”明顯高於同組其他令牌 | 大上下文、長輸出、高頻呼叫或重複任務 | 結合請求數、平均耗時和錯誤日誌，定位具體服務或成員 |
| “快取命中率”高但“快取請求佔比”低 | 少量大請求命中快取 | 檢查是否只有固定任務在複用上下文 |
| “快取請求佔比”高但“平均快取Tokens”低 | 很多請求命中快取，但每次收益較小 | 檢查上下文是否過短或快取內容不穩定 |
| 單個令牌“平均耗時”明顯偏高 | 客戶端任務較重、上下文長、輸出長或上游慢 | 對比該令牌的請求數、快取、失敗原因和單條日誌 |

## 支援排查需要的資訊

遇到簡單問題時，建議先檢視 [錯誤日誌說明](/zh-TW/error-logs) 和 [分組健康狀態說明](/zh-TW/group-health) 自查。仍無法解決時，可以在 `console/log` 的錯誤日誌詳情中點選複製圖示，一鍵複製排查內容。聯絡支援時，建議一次性提供以下資訊給技術排查，減少來回確認：

- 使用者 ID
- 時間範圍：問題開始和最後出現的時間
- 分組名：`group`
- 模型名：請求使用的模型
- 狀態碼：例如 `429`、`413`、`502`、`503`
- 錯誤內容：`error_reasons.content`
- 請求 ID：單條日誌或介面響應中的 `request_id`
- 影響範圍：單個 Token、單個模型、單個分組，還是多個分組同時異常

<Callout type="idea" title="快速結論">
  `401` / `403` 多看許可權，`413` 多看請求體，`429` 多看頻率和額度，`502` / `504` / `524` 多看上游和長任務，`503` 多看資源是否暫不可用。
</Callout>
