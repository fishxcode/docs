這頁解釋 FishXCode 的計費口徑、令牌分組和套餐頁面之間的關係。你可以把它當成購買和建立 Key 前的檢查清單：先看定價頁確認模型和套餐，再看分組決定 Key 能呼叫什麼，最後用使用日誌和分組健康狀態核對實際消耗。

<Callout type="idea" title="當前口徑">
  當前定價頁口徑為 **49 個模型、14 個可選分組**。模型、價格、分組和可售狀態會隨上游資源調整，最終以 [定價頁](https://fishxcode.com/pricing?currency=CNY) 和控制台展示為準。
</Callout>

## 一、先區分三種計費入口

FishXCode 的費用不是單一規則。實際使用時，先判斷你在用哪種入口：

| 入口 | 看什麼 | 適合什麼場景 |
| - | - | - |
| 按量使用 | 模型基礎價格、輸入/輸出/快取倍率、令牌分組 | 按餘額呼叫 API、臨時測試、多模型混用 |
| 訂閱套餐 | 有效期、總額度、每日上限、每月上限、適用分組 | 團隊固定預算、Codex / Claude 系列長期使用 |
| 令牌分組 | 這個 Key 可以呼叫哪些模型、走哪個資源池、按什麼倍率扣費 | 建立 Key、拆分專案、團隊成本歸因 |

相關套餐規則可以和 [訂閱套餐總覽](/zh-TW/subscription-plans) 一起看：本頁解釋“模型、倍率、分組如何影響扣費”，套餐頁解釋“購買後額度、有效期、次數和上限如何生效”。

## 二、定價頁模組：先看套餐卡片

定價頁的套餐卡片適合快速判斷：這個套餐給多少額度或次數、多久有效、每天能用多少、是否有特殊折算規則。

![訂閱套餐列表示例](/img/plans/subscription-plans.png)

讀套餐卡片時重點看這些欄位：

| 欄位 | 含義 | 怎麼判斷 |
| - | - | - |
| 當前價格 | 本次購買價格和有效期 | 例如 `¥320.00 / 1個月` 表示一個月價格 |
| 單次成本 | 套餐價格除以總次數後的參考成本 | 用來比較同類按次套餐價效比 |
| 套餐上限 | 當前套餐總額度或總次數 | 例如 `15000 次` 表示本套餐最多累計 15000 次基礎請求 |
| 每天上限 | 單日最多可用額度或次數 | 例如 `500 次/天`，當天達到後通常需要等重置 |
| 重置時間 | 週期上限恢復時間 | 例如 `每天 08:00:00 重置` |
| 適用範圍 | 套餐繫結的分組、模型和供應商 | 例如 `sub_plan_claude_mini_plus · 9 模型 · 2 供應商` |
| 按次計費說明 | 特殊模型是否按倍率折算次數 | 例如 Claude Opus 4.8、GPT-5.5 按 `2.5 * 1 次` 計算 |

<Callout type="idea" title="例子：按次套餐怎麼扣">
  某套餐寫著 `500次/天，月共15000次`，並說明 `Claude Opus 4.8、GPT-5.5 按 2.5 * 1 次計算`。

  普通模型成功請求 1 次，通常記 1 次；Claude Opus 4.8 或 GPT-5.5 成功請求 1 次，會按 2.5 次計入套餐用量。也就是說，當天如果一直使用這類高倍率模型，約 200 次成功請求就可能達到 `500次/天` 的日上限。
</Callout>

## 三、套餐權益模組：看清上限、重置和適用模型

開啟套餐權益或詳情頁後，可以看到更細的權益欄位。這個模組用於確認“買了之後到底能用什麼”。

![按次套餐權益示例](/img/plans/by-number-of-times.png)

這張圖裡可以看到：

- **每天上限**：單日最多可用次數。
- **套餐上限**：整個有效期內總次數。
- **什麼時候重置**：日上限的恢復時間。
- **開放購買時間**：某些套餐只在指定時間段開放購買。
- **供應商**：套餐覆蓋的上游供應商。
- **可用模型**：購買後該套餐分組能呼叫的模型列表。
- **升級分組**：購買後自動進入或繫結的分組，例如 `sub_plan_claude_mini_max`。

<Callout type="warn" title="套餐頁和分組頁要一起看">
  套餐頁告訴你“額度和上限”，分組告訴你“模型和通道”。如果套餐顯示支援某個升級分組，但你的實際 Key 沒繫結到該套餐或該分組，請求仍可能走餘額或報許可權錯誤。
</Callout>

## 四、購買模組：支付前核對有效期和開通方式

點選購買後會進入購買彈窗。這個模組用於最後確認：買哪個套餐、多少錢、有效期多長、是否自動開通。

![購買訂閱套餐示例](/img/plans/buyplan.png)

購買前重點核對：

| 欄位 | 為什麼重要 |
| - | - |
| 當前價格 | 判斷本次支付金額，避免選錯套餐 |
| 有效期 | 到期後套餐權益會失效 |
| Token 額度 / 次數 | 決定本套餐可消耗的總量 |
| 套餐型別 | 自動開通、人工發放或其他交付方式會影響生效時間 |
| 支付方式 | 確認支付寶、微信或其他支付入口 |
| 購買須知 | 退款、開通、限購和售後規則以頁面展示為準 |

如果你只想臨時測試模型，不一定要先買套餐，也可以先用餘額按量呼叫。

## 五、按量使用：用餘額直接呼叫模型

按量使用就是不先購買固定套餐，直接用帳戶餘額呼叫模型。它適合先跑通工具、低頻呼叫、多模型混用，或者還不確定要買哪類套餐的情況。

按量使用的基本路徑：

1. 在 [定價頁](https://fishxcode.com/pricing?currency=CNY) 確認目標模型支援哪些分組。
2. 在 **控制台 → 令牌管理** 建立普通令牌，選擇合適的令牌分組。
3. 把 Key 配置到 Claude Code、Codex、Cursor、RooCode 或自有程式。
4. 每次成功請求後，系統按模型價格、輸入/輸出 Token、快取命中和分組倍率扣減餘額。
5. 在 **控制台 → 使用日誌** 核對實際消耗。

按量扣費可以理解為：

```text
實際消耗 ≈ 模型基礎消耗 × 分組倍率 + 輸出/快取等差異項
```

這裡的“模型基礎消耗”不是固定值，會隨輸入長度、輸出長度、快取命中、模型本身價格變化。圖片、影片等固定價格模型不適合用普通文本 Token 方式估算。

餘額按量和套餐的區別：

| 型別 | 特點 | 適合場景 |
| - | - | - |
| 餘額按量 | 用多少扣多少，餘額不足時停止呼叫 | 臨時測試、多模型混用、低頻使用 |
| Codex 套餐 | 通常按有效期和額度管理 | Codex / GPT 程式設計任務、團隊固定預算 |
| 按次套餐 | 按成功請求次數累計，並可能有日上限 | 想控制請求次數預算 |
| ClaudeMax 套餐 | 偏帳號權益和 Claude Code 使用路徑 | Claude Code 官方號訂閱場景 |

<Callout type="idea" title="例子：按量更適合什麼">
  如果你只是想測試某個工具能不能連通 FishXCode，先用 `default` 或目標模型推薦分組建立普通令牌，再發起少量請求即可。確認模型、分組和客戶端配置都正確後，再根據用量決定是否購買 Codex 套餐、按次套餐或 ClaudeMax 套餐。
</Callout>

<Callout type="warn" title="按量也受分組限制">
  帳戶有餘額不代表任何 Key 都能呼叫任何模型。模型是否可用仍取決於令牌分組。如果報 `model not found`、`model not available` 或許可權錯誤，先檢查 Key 的分組是否包含目標模型。
</Callout>

## 六、令牌模組：分組決定 Key 的模型範圍

令牌分組可以理解為 **這個 API Key 的可用模型範圍 + 扣費倍率規則 + 上游資源池**。建立 Key 時一定要選對分組。

![建立令牌時選擇分組](/img/start/api-06-token-create.png)

建立普通令牌時重點看：

- **令牌分組**：決定這個 Key 能呼叫哪些模型。
- **額度設定**：限制當前 Key 最多可消耗多少額度；無限額度不代表不扣費，仍受帳戶餘額或套餐限制。
- **模型限制列表**：非必要不建議限制，除非你明確只允許某幾個模型。
- **IP 白名單**：適合服務端固定出口；個人本地開發慎用，避免 IP 變化後無法呼叫。

分組選錯時，常見表現包括：

- 模型列表裡看得到模型，但當前 Key 呼叫時報 `model not found`、`model not available` 或許可權錯誤。
- 能呼叫模型，但扣費倍率、快取表現或穩定性不是預期的那一檔。
- 套餐 Key 和普通餘額 Key 混用，導致額度走錯帳戶或統計口徑不清晰。

## 七、套餐令牌模組：基於套餐建立團隊 Key

購買套餐後，系統可能自動生成套餐訪問令牌，也可以基於套餐建立新的團隊令牌。這樣做適合多人共享套餐額度，但又需要區分成員或專案消耗。

![基於套餐建立令牌示例](/img/plans/create.png)

基於套餐建立令牌時，重點看這幾項：

| 欄位 | 說明 |
| - | - |
| 基於套餐建立 | 選擇要繫結的套餐；繫結後到期時間、分組和模型限制會跟隨套餐 |
| 名稱 | 建議按成員、專案或服務命名，方便日誌篩選 |
| 令牌分組 | 預設跟隨套餐或使用者分組；不要隨意切到不匹配的分組 |
| 過期時間 | 通常不應超過套餐有效期 |
| 套餐令牌額度 | 用來限制這個子 Key 最多消耗多少套餐額度 |

<Callout type="idea" title="例子：團隊怎麼拆 Key">
  一個 Codex 套餐給 5 個成員共用時，不建議所有人共用同一個 Key。可以為每個成員建立獨立令牌，例如 `codex-zhangsan`、`codex-lisi`。後續在使用日誌或分組健康狀態裡，就能直接看出是誰消耗高、誰錯誤多、哪個專案需要限額。
</Callout>

## 九、倍率和扣費例子

倍率只是在模型基礎價格上再乘一個係數。倍率越低，通常同一模型同一請求的扣費越低。

| 模型基礎消耗 | 分組或模型倍率 | 估算扣除 |
| - | - | - |
| 10 額度 | `1x` | 10 額度 |
| 10 額度 | `0.5x` | 5 額度 |
| 10 額度 | `0.1x` | 1 額度 |
| 10 額度 | `2.5x` | 25 額度 |

更貼近呼叫的例子：

| 場景 | 估算方式 |
| - | - |
| 某模型基礎消耗 8 額度，走 `1x` 口徑 | 約扣 8 額度 |
| 同一請求走 `0.5x` 口徑 | 約扣 4 額度 |
| 同一請求走 `2.5x` 模型倍率 | 約扣 20 額度 |
| 命中快取的長上下文請求 | 快取部分通常更便宜，最終以日誌記錄為準 |

<Callout type="warn" title="不要只看倍率">
  倍率不是唯一價格。不同模型的基礎價格、輸出倍率、快取倍率差異很大；圖片、影片模型還可能是固定價格。做成本估算時，請以定價頁或控制台模型列表中的當前價格為準。
</Callout>

## 十、使用後怎麼核對實際消耗

呼叫後不要只憑估算判斷費用，應該去 **控制台 → 使用日誌** 查實際消耗。團隊或套餐場景下，再結合 **分組健康狀態** 判斷是否是單個 Key、單個使用者或整個分組的問題。

![分組健康狀態示例](/img/plans/statistics.png)

分組健康狀態適合回答這些問題：

| 問題 | 看哪個欄位 |
| - | - |
| 哪個分組消耗最高 | 分組、消耗、請求數 |
| 是否只有某個成員異常 | 使用者 / 令牌明細行 |
| 快取有沒有生效 | 快取命中率、快取 Tokens、快取請求佔比 |
| 是否是資源池問題 | 分組成功率、錯誤數、失敗原因 |
| 是否是長上下文或大輸出導致費用高 | 單次成功消耗、平均耗時、快取 Tokens |

<Callout type="idea" title="例子：團隊復盤">
  如果 `codex_sub` 分組整體成功率正常，但某個成員令牌的單次成功消耗明顯高於其他成員，優先檢查該成員是否在跑長上下文、大輸出或重複任務。如果整個分組成功率下降，再考慮分組資源池、上游狀態或套餐許可權問題。
</Callout>

## 十一、快速選擇建議

| 使用場景 | 建議優先檢視 | 原因 |
| - | - | - |
| 不確定要用什麼 | `default` 或控制台推薦分組 | 先驗證工具配置是否正確 |
| Claude Code 穩定使用 | `cc-max`、`cc_max`、ClaudeMax 系列 | 更貼近 Claude Code 使用路徑 |
| 自有客戶端接 Claude | `cc_export` | 不限制客戶端，適合第三方工具 |
| Codex / GPT 程式設計 | `codex_plus`、`codex_pro`、`codex_sub_june` | 面向程式碼和工具呼叫任務 |
| 多系列統一入口 | `OpenRouter` | 適合統一入口呼叫 Claude、Codex 等多系列模型 |
| Gemini CLI 或多模態 | `gemini` | 覆蓋 Gemini 系列模型 |
| Grok 模型 | `grok` | 覆蓋 Grok 對話、推理和視覺任務 |
| DeepSeek 模型 | `deepseek` | 覆蓋 DeepSeek 官方渠道 |
| 團隊或專案拆分 | 為成員或專案建立獨立令牌 | 便於額度控制、成本分攤和日誌排查 |

## 十二、排查消費或許可權異常

遇到消費異常或模型不可用時，建議按這個順序排查：

1. 確認當前 Key 繫結的令牌分組是否包含目標模型。
2. 確認餘額、套餐有效期、日上限、月上限或總額度是否充足。
3. 檢視 **控制台 → 使用日誌**，按時間、模型、Token、分組、請求 ID 篩選。
4. 對比 [分組健康狀態](/zh-TW/group-health)，判斷是單個 Token 問題還是分組資源池問題。
5. 如果仍無法判斷，聯絡支援時提供訂單號、令牌名稱、分組、模型名、請求時間和請求 ID。
