## 3. How multipliers are calculated

The multiplier is a factor applied on top of a model's base price. The lower the multiplier, the less the same model and the same request cost:

```text
Actual usage ≈ model base usage × group multiplier
```

<RatioExampleTable base={10} groups={['codex-team', 'codex-plus', 'claude', 'claudemax']} />

The model base usage here is not a fixed value: it varies with input length, output length, cache hits, and the model's own price. Cached portions are usually cheaper.

<Callout type="warn" title="Don't judge by the multiplier alone">
  The multiplier is not the whole price. Base prices, output multipliers, and cache multipliers differ greatly between models; image and video models may even use flat pricing. When estimating costs, rely on the current prices on the pricing page or in the console's model list.
</Callout>

## 4. Pick the right group when creating an API Key

When you create an API Key under **Console → API Keys**, the key's group defines the models it can call, the billing multiplier, and the upstream resource pool — make sure to choose it correctly.

![Choosing a group when creating an API Key](/img/start/api-v2-06-token-create.png)

When creating an API Key, pay attention to:

- **Group**: determines which models this key can call and at what multiplier usage is billed.
- **Quota settings**: cap how much this key may consume. Unlimited quota does not mean free — usage is still limited by your account balance.
- **Model restriction list**: avoid restricting unless you clearly want to allow only a few models.
- **IP allowlist**: suits servers with a fixed outbound IP; use cautiously for personal local development to avoid broken calls after an IP change.

Common symptoms of picking the wrong group:

- The model shows up in the model list, but calls with the current key fail with `model not found`, `model not available`, or a permission error.
- The model works, but the billed multiplier or the stability is not the tier you expected.

## 6. Verify actual usage afterwards

After making calls, verify actual consumption against the records in **Console → Usage Logs**. In team scenarios, use the group and user/key breakdown rows in the logs to tell whether the issue is one key, one member, or the whole group.

| Question | Which fields to look at |
| - | - |
| Which group consumed the most | Group, consumption, request count |
| Is only one member abnormal | User / key detail rows |
| Did the cache take effect | Cache hit rate, cached tokens, share of cached requests |
| Is it a resource-pool issue | Group success rate, error count, failure reasons |
| Is the high cost due to long context or large outputs | Per-success consumption, average duration, cached tokens |

## 7. Usage notes

1. Different groups map to different resource pools — choose by use case.
2. For long Claude conversations, make good use of context caching. Actual cache hits depend on client configuration, the model, and request intervals.
3. Group multipliers, model availability, and resource conditions are subject to the site's real-time information.

## 8. Troubleshooting usage or permission issues

When consumption looks wrong or a model is unavailable, troubleshoot in this order:

1. Confirm the group bound to the current key includes the target model.
2. Confirm that your account balance is sufficient.
3. Check **Console → Usage Logs**, filtering by time, model, key, group, or request ID.
4. Filter by the group column in the logs to tell whether it is a single-key issue or a group resource-pool issue.
5. If it is still unclear, contact support with the order number, key name, group, model name, request time, and request ID.
